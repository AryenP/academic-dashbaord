# Decisions

Changes from `docs/SPEC.md` and `docs/BUILD_PROMPT.md`, with the reason for each.

- **2026-10-20 · Sync calls Deploy directly (`workflow_call`) instead of Deploy listening for `workflow_run`.** Pushes made with `GITHUB_TOKEN` don't trigger other workflows, and calling it only when the plan changed avoids a rebuild every 15 minutes.
- **2026-10-20 · The build bundles a copy of `public/data.json`.** The runway draws instantly and offline, then the page fetches the live file, like the old inline snapshot did.
- **2026-10-20 · Build-time config comes from repo secrets** (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SPOTIFY_CLIENT_ID`), the same secrets the sync uses, so there's one place to set them. All three are public by design; they're secrets only for convenience.
- **2026-10-20 · Screenshots are written for review, not diffed.** `tests/e2e/screens.spec.ts` saves them to `tests/e2e/__screenshots__/` (git-ignored). Pixel diffs across OS font rendering would be noise in CI.
- **2026-10-20 · Added `.github/workflows/ci.yml`** to run `npm run check` on every push, so the Deploy workflow only needs lint, unit tests and the build.
- **2026-10-20 · Tests run in Pacific time** (`TZ` for Vitest, `timezoneId` for Playwright). The plan's day boundaries are Pacific, and CI runners are UTC.
- **2026-10-20 · `profiles.is_owner`.** The first account to sign up is the owner, and `public_daily_totals()` shows only the owner's totals. Nobody can change `is_owner` from the client. After signing in once, turn off sign-ups in Supabase (Authentication → Sign In / Providers → "Allow new users to sign up").
- **2026-10-20 · `sessions.paused_at`.** Not in the original schema. Pause is a state, and the timer is derived from timestamps, so the start of the current pause has to be stored. Resuming folds it into `paused_seconds`.
- **2026-10-20 · Session transitions are SQL functions** (`pause_session`, `resume_session`, `start_break`, `end_break`, `end_session`). The web app and the phone function share them, they're atomic, and they use the database clock. They run as the caller, so RLS still applies.
- **2026-10-20 · Only one unfinished session per person** (partial unique index). A second "start" from the phone is a no-op.
- **2026-10-20 · Rate limit uses a `phone_rate` table** (per token hash, per minute) behind a service-role-only function. Supabase has no built-in KV.
- **2026-10-20 · Database and function tests.** `npm run test:db` runs the RLS tests against a local Supabase, and `npm run test:fn` runs the phone-event handler tests in Deno. CI runs both in a `backend` job.
- **2026-10-20 · `session_breaks.paused_before`.** Each break stores how much pause time the session had when the break began, so "time to next break" is exact even when you pause and take breaks in the same session.
- **2026-10-20 · The timer corrects for device clock skew.** It learns the server-minus-device offset from the timestamps the server writes on start and break, so a phone whose clock is off still shows the right time.
- **2026-10-20 · On the public runway, visitors see a daily-total gauge, not time-accurate bars.** `public_daily_totals()` deliberately has no times of day. The owner sees each session at its real time.
- **2026-10-20 · Readiness counts every session for that course before the exam,** not only sessions linked to a plan block. Studying off-plan still counts.
- **2026-10-20 · Stats charts are CSS, not d3.** The bars and heatmap are simple enough that d3 would only add bundle weight.
- **2026-10-20 · Signed-in browser tests** (`npm run test:e2e:db`) run against a local Supabase and sign in by placing a real session in the browser. CI runs them in the `backend` job.
- **2026-10-20 · A pickup is opening a listed app while none is already open.** Switching straight from Instagram to TikTok is one pickup, not two. That matches what "picking up your phone" means. Overlapping app intervals are merged, so phone time is never double-counted.
- **2026-10-20 · Pauses count as focus time in focus %.** Pauses aren't timestamped individually, so the denominator is the session minus breaks, as in the spec. Phone use during a pause counts like any other.
- **2026-10-20 · `src/lib/focus.ts` has no imports**, so the Edge Function imports the same file. Metrics are frozen identically whether a session ends on the web or from the phone.
- **2026-10-20 · The phone-event function answers CORS preflights.** The setup page's "send a test from this browser" needs it. No cookies are involved and every request needs the token, so this exposes nothing.
- **2026-10-20 · The phone token is shown once and held only in memory** for that tab, so the setup guide can fill it in. The database stores its sha256. Losing it means replacing it.
- **2026-10-20 · Spotify redirects to `spotify.html`, not the site root.** Supabase's magic link also returns to the root with `?code=`, and the two would collide. The callback page hands the code to the app and goes to Settings. Redirect URIs to register: `https://aryenp.github.io/academic-dashbaord/spotify.html` and `http://127.0.0.1:5173/academic-dashbaord/spotify.html`.
- **2026-10-20 · Session cues fire on transitions this device sees**, including ones made on another device or by the phone Shortcut, but not on page load. Spotify tokens are per device, so normally only one device sends them.
- **2026-10-20 · A 403 means "needs Premium" only when Spotify says `PREMIUM_REQUIRED`.** Other 403s in Development Mode usually mean the account isn't on the app's user list, and the message says so.
- **2026-10-20 · The embed fallback is a playlist link saved in Settings.** It works with no login (30-second previews unless the browser is signed in to Spotify).
- **2026-10-20 · Spotify is tested against a network-level fake** (`tests/e2e-db/fakeSpotify.ts`) covering the PKCE redirect, token exchange, player calls and error responses, since CI can't use a real Premium account.
- **2026-10-20 · Public visibility has three levels** (`profiles.public_level`, migration 0002): daily totals and readiness, readiness only, or just the runway. It replaces the `public_totals` flag. Readiness-only uses a second function, `public_prep_minutes()`, that returns prep minutes per exam and nothing per day.
- **2026-10-20 · Course colors have accessible "ink" and "on-fill" variants.** The fills stay as designed. Course-colored text uses a darker ink shade, and labels on teal and orange blocks are dark, so everything meets 4.5:1, including on the "now" highlight. Light-mode warn and red text are a shade darker for the same reason.
- **2026-10-20 · Runway blocks are `role="img"` with a full label,** not buttons. They show a tooltip, and nothing happens when you activate them.
- **2026-10-20 · Offline writes are a replayed action queue, not a generic request queue.** Session actions apply on the device at once (mirroring the SQL functions) and replay in order with their original times. Rating and note need a connection, and the end screen says so.
- **2026-10-20 · The service worker is generated per build** with the full file list and a build id. Every view works offline after one visit, and each deploy replaces the old cache rather than adding to it.
- **2026-10-20 · Only the runway is in the first bundle.** The other views load on demand. Lighthouse mobile: 96 performance, 100 accessibility, 100 best practices.

## v2

- **2026-10-21 · One `plan_items` table, not `exams` + `deadlines` + `plan_blocks`.** The runway draws them as one list and every v1 component takes a mixed list, so a `kind` column with the extra fields (weight, status, score, reason, accepted) keeps the frontend and the RLS surface small. Later phases add columns, not tables.
- **2026-10-21 · `sessions.plan_block_id` is dropped and replaced by `plan_item_id` (uuid, on delete set null).** v1's links pointed at JSON ids that no longer exist; readiness never used them (it counts every session for the course).
- **2026-10-21 · School-email rule is `.edu`, `.edu.<cc>` or `.ac.<cc>`,** enforced by a `before insert` trigger on `auth.users` and mirrored in `src/lib/email.ts`. Existing accounts are untouched. International students exist; "school email" is the real rule, not ".edu".
- **2026-10-21 · Account deletion is a SQL function (`delete_my_account`), not an Edge Function.** It deletes the caller's `auth.users` row as a definer and everything cascades. Vault secrets (Phase 1) will cascade through a trigger on `calendar_sources`.
- **2026-10-21 · Share pages are `#/u/<handle>` and sharing defaults to `off`.** Four levels (`off`, `runway`, `readiness`, `totals`) replace v1's three; `off` is the new default because the public portfolio is now the demo landing page. The four share functions take a handle and return nothing at `off`.
- **2026-10-21 · Timezone is per profile** (`profiles.timezone`, default Pacific). The totals function groups days in it, and the frontend formats every plan time in it, so the runway reads wall time from the string exactly as v1 did.
- **2026-10-21 · The landing page is prerendered into `index.html` at build time** (`scripts/prerender.tsx` with react-dom/server, run after `vite build`) and the client replaces it with the live component rather than hydrating. The static board is an empty shell of the same height: the demo's dates depend on the day, so hydrating would mismatch. Crawlers get the text; nothing shifts.
- **2026-10-21 · Signed-out visitors at the root never download the app chunk.** `src/main.tsx` mounts the landing page alone unless there is a session, a hash route, or an auth callback in the URL.
- **2026-10-21 · The GitHub keep-alive stays** (`.github/workflows/keepalive.yml`, daily) instead of `pg_cron`, because Supabase counts API requests, not database activity, when deciding to pause a free project. The calendar sync workflow, `scripts/sync.py` and `public/data.json` are deleted; git history keeps them.
- **2026-10-21 · Course colors are six slots per user** (`courses.color`): five colors and a gray for "General" and overflow. v1's hardcoded course list is gone; `setCourseSlots()` fills a registry from the plan so `courseVars(code)` keeps working everywhere sessions store a course code.
- **2026-10-21 · "Continue with Google" ships behind `VITE_GOOGLE_SIGNIN=true`.** The button needs a Google OAuth client configured in Supabase (Aryen's step); until then it's hidden rather than broken.
- **2026-10-21 · Phase 0 ships a hand-entry form (`AddItem`)** so a new account has something to do before calendar sources arrive in Phase 1, and the empty runway always has a next action.
- **2026-10-21 · The sync is triggered by GitHub Actions every 15 minutes** (`.github/workflows/sync.yml` → `sync-sources` with a shared `SYNC_KEY`), not `pg_cron` + `pg_net`. Supabase pauses free projects on API inactivity, so an outside caller is needed anyway; this is v1's proven mechanism and it replaces the keep-alive. The function also syncs one source on demand with the person's JWT.
- **2026-10-21 · Calendar addresses live in Supabase Vault.** `add_calendar_source()` (security definer) writes the secret and the row; `secret_id` has no client grant; `source_url()` is service-role only; a delete trigger removes the secret. Feeds are fetched with `If-None-Match` so unchanged feeds are a 304.
- **2026-10-21 · Events are stored raw; the title rules fill `kind` and `course_code` on every sync.** The rules are v1's, generalized (`supabase/functions/_shared/classify.ts`): course codes in any spacing or case, a stoplist of look-alikes (HW 2, Week 5, Room 115), Canvas's `[Course]` bracket and `event-assignment` UIDs. A person's `override` on an event survives re-syncs. Phase 2's AI pass gets the low-confidence rows.
- **2026-10-21 · All-day events: a deadline is due at 11:00–11:59 PM that day, an exam fills 8 AM–10 PM, anything else isn't drawn.** The runway has a time axis; an all-day holiday block would hide the day.
- **2026-10-21 · Duplicates collapse by title and start time (±5 min)**, so an assignment in both Canvas and Google becomes one plan item linked from two events. Removing a source removes only the plan items no live event points at.
- **2026-10-21 · The sync window is 30 days back and 180 ahead, at most 2000 occurrences per feed and 400 per recurring rule.** Enough for a year-long class schedule; a cap is reported as `truncated` rather than silently cut.
- **2026-10-21 · `validate-source` is rate-limited to 20 checks a minute per person and `sync-sources` to 10**, through the existing `phone_rate` counter (keyed `validate:<uid>`), rather than a new table.
- **2026-10-21 · The setup diagrams are schematic SVG, drawn in code** (`src/connect/guides.tsx`), not screenshots: they follow the theme, stay crisp at any size, and don't go stale pixel by pixel when a vendor moves a button.
- **2026-10-21 · A new account is sent to `#/connect` once** (`profiles.onboarding.connect_seen`); after that the empty runway offers "Connect a calendar" and "Add by hand".
- **2026-10-21 · The local functions env file lives at the repo root (`.env.functions.local`), never under `supabase/functions/`.** `supabase functions deploy` (CLI 2.121) uploads `supabase/functions/.env` *and* `.env.local` into the functions' environment, which silently replaced the real `SYNC_KEY` with the local placeholder twice. Found with a kept diagnostics function (`supabase/functions/diag`, reports secret lengths and never values). The real key is set with `supabase secrets set` and checked with `diag` after deploys.
- **2026-10-21 · Sign-in emails need a real SMTP provider before launch.** Supabase's built-in sender caps at a few emails an hour per project (Aryen hit "email rate limit exceeded" on his second sign-in). `email_sent` is raised to 60 in config.toml but only applies once `[auth.email.smtp]` is enabled with a provider (Resend or similar); setting that up is Aryen's step. Until then, Google sign-in is the other way around the cap. The app shows the limit in plain words and reminds people the last link still works for an hour.
- **2026-10-21 · The AI reading lives on the event row (`ai_*` columns), and what's drawn follows override > AI > rules** (`src/lib/reading.ts`, shared with the functions). The rules' reading stays in `kind`/`course_code` so an AI or override change is visible and reversible; an AI reading applies only while `ai_hash` matches the event's hash, so an edited event is re-read rather than kept stale.
- **2026-10-21 · The rules' reading is drawn right away; the review screen is where it gets corrected.** The spec said nothing becomes a plan until the person confirms. In practice a runway that stays empty until a confirm screen is a worse first minute than one that draws what the rules found (v1 drew the rules' reading for a year). The AI's readings and the person's edits are applied by rebuilding the plan from stored events (`rebuildPlan`), never by a second fetch, so an `.ics` upload is editable too.
- **2026-10-21 · One Claude call per batch of up to 150 events, `claude-opus-5-5` at `effort: "low"`, structured output (`output_config.format`, JSON schema), the system prompt cached.** The model is a row in `app_config` (`ai_model_classify`), so switching to Haiku 5.5 after the eval is one update, not a deploy. Only events the rules were unsure about (confidence < 0.85) go to the model unless the person asks to read everything.
- **2026-10-21 · AI spend is metered in `ai_usage` per person per month, against `ai_user_monthly_cents` (200) and `ai_global_monthly_cents` (5000) in `app_config`; the function refuses before calling when either is spent.** Cost is computed from the usage block with a price table in `ai.ts` (cache reads at a tenth of input). A nightly pass runs from the sync workflow with the same key.
- **2026-10-21 · Title rules learn the person's courses:** `classify()` takes `knownCourses`, so "Midterm 1 (140A)" and "📚 140A practice" resolve to DSC 140A once that course exists. Course-less "due" items are deadlines with no course (0.5), not personal, so they show under "Which course?" on the review screen instead of vanishing.
- **2026-10-21 · The eval set is Aryen's own Fall 2026 plan plus Canvas, class, work and personal events** (`eval/classify.json`, 48 events). The rules score 100 % on kind and 29 % on course on their own; the course gap is the AI's job. `npm run eval:classify -- --ai` scores a model once `ANTHROPIC_API_KEY` is set.
- **2026-10-21 · `@anthropic-ai/sdk` is pinned to 0.135.0 in the functions**, not 1.0.0: Deno refuses packages published less than a day ago by default, and the edge runtime needs the same specifier the tests use.
- **2026-10-21 · Claude Haiku 5.5 is the default reader** (`app_config.ai_model_classify`, migration 0006), on Aryen's call for cost, ahead of the eval. The eval (`npm run eval:classify -- --ai --model …`) decides whether it stays; Opus 5.5 is one `update` away.
- **2026-10-21 · The Anthropic key is set by Aryen, never by the assistant:** `scripts/set-ai-key.sh` reads it from the terminal, sets the Supabase secret, writes the local functions env, and runs the eval on both models. A key that was pasted in a chat is treated as exposed and rotated.
- **2026-10-21 · Shared function secrets (the sync key, the Anthropic key) live in Vault** (`set_app_secret` / `app_secret`, migration 0007, service role only) **and the functions read them per call**; the environment is only a fallback. The hosted runtime kept serving a placeholder `SYNC_KEY` for hours after `supabase secrets set` changed it, through redeploys and a project restart. The database is never stale.

### Phase 3

- **2026-10-21 · Free time is computed in code; the model only places blocks into it.** `freeSlots()` takes the study window, days off, and every accepted item (padded 15 minutes); Claude gets exams (weight, hours planned, hours studied) and the slots, and answers blocks with reasons. Every block is then checked (`validate()`): inside a slot, before its exam, no overlap, under the daily cap; what fails is dropped. If the AI is off, out of budget, or fails, a plain allocator (`allocate()`) fills the same slots, so drafting always works and tests are deterministic (`ai_enabled` is switched off in the browser tests that draft).
- **2026-10-21 · Proposals are `plan_items` with `accepted = false`**, drawn dashed with the reason in the tooltip, excluded from totals, prep hours, the feed and share pages. Accept all or one; discard deletes. A new draft replaces unaccepted proposals.
- **2026-10-21 · "Behind" means the accepted study blocks that already passed for an exam under 10 days out add up to 2+ hours more than what was actually logged for that course since the first of them.** The nudge drafts for that exam only.
- **2026-10-21 · The plan feed is a per-user token in the URL** (`access_tokens`, purpose `feed`, sha256 stored, made and shown once in Settings), served by `plan-feed` as iCalendar with stable UIDs so subscribers update in place. Google refreshes subscribed feeds every few hours; nothing to do about that.
- **2026-10-21 · Submissions are a status on the deadline** (`open`, `submitted`, `missed`, with `submitted_at` and `submitted_by`), ticked on the runway or in the agenda, set by the extension, or answered to "Did you submit…?" which appears for a deadline that passed in the last 3 days after a study block for its course. The weekly review counts on time, late, missed and open.
- **2026-10-21 · The extension is content-script only in this version:** it reads a Gradescope course page or a Canvas assignments page when you open one and posts to `import-items` with a per-user token (`access_tokens`, purpose `extension`). No background polling: that would need the extension to fetch pages itself, and reviewers ask hard questions about that. Scores go only when the popup's switch is on. The parsers run on saved page fixtures in tests (linkedom); Gradescope and Canvas markup changes will show up there first.
- **2026-10-21 · Imported deadlines match existing ones by normalized title and course** (and a due date within 36 h), so a Canvas-feed deadline and the same assignment on Gradescope stay one item; the extension updates its status and score. Items with no due date aren't drawn.
- **2026-10-21 · Planning settings live in `profiles.settings.planning`** (hours per day, not before, not after, block length, days off); no new table.

### Phase 4

- **2026-10-21 · Classmates need no roster:** a course is matched by school (email domain) and course code, and only for people who turned "Show me to classmates" on for that course (`courses.visible`). Seeing the list requires being visible in it too (reciprocity, enforced in `classmates()`). What a classmate sees of you follows your share level: name and course always once visible; hours this week only at `totals`; streak and exam readiness at `readiness` or `totals`. Never notes, phone data or grades. Someone at another school never appears, same code or not.
- **2026-10-21 · Friends are requests by handle, accepted by the other side**, in a `friends` table nobody writes directly (functions only). A friend sees your share-level stats and the courses you made visible. Removing works from either side.
- **2026-10-21 · The runway's social line is one count:** "N classmates studied today", from `classmate_pulse()`, which only counts classmates sharing totals. No leaderboard yet; the per-course list with readiness bars is the comparison, opt-in on both sides.
- **2026-10-21 · The Courses screen lists every course from the `courses` table**, not only those with calendar events, so a course added by hand or from the demo has a card to opt in on. "Not a course" now deletes the course row (its plan items cascade; events keep a `personal` override).
- **2026-10-21 · Syllabus PDFs go to the model as a document block and come back as structured output with a page and quote per item**; the API's citations feature can't be combined with structured output, so the page and quote are fields in the schema. Nothing from the PDF is stored: the exams and dated deadlines become proposals (`accepted = false`) with `reason` = "Syllabus, p. N: “…”", accepted on the runway like planner drafts. Undated items ("Final: TBA") are counted and left out.
- **2026-10-21 · The AI weekly review is three sentences, written once per week per person and kept** (`weekly_reviews`); the facts are computed server-side from sessions and plan items (never notes), and "write it again" rewrites it. Opening the Week page writes the current week's review on first view: one short Haiku call.
- **2026-10-21 · Grades feedback is a list, not a model:** the Week page shows scores that arrived through the extension next to the hours put into that course that week. Correlations wait for Phase 5's signals.
- **2026-10-21 · Google Calendar OAuth is deferred**: it needs Aryen's Google Cloud project, consent screen and the calendar-scope review (weeks). The iCal address path covers the same calendars today; the OAuth path lands when the review clears.
- **2026-10-22 · Google sign-in is wired through Google Cloud project `runway-512406`** (consent screen "Runway", external, published; scopes openid/email/profile only, so no verification review; authorized domains `aryenp.github.io` and the Supabase project domain; web client "Runway web" with the Supabase `/auth/v1/callback` redirect). The client secret is pasted into the Supabase dashboard by Aryen and never touches the repo; `config.toml` carries the public client ID and reads the secret from `SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET` so a config push can't drop the provider. The button on the sign-in screen is gated by the `GOOGLE_SIGNIN` repo variable (now `true`). Calendar scope and its review stay deferred.
- **2026-10-22 · Google sign-in verified live** (Aryen's UCSD account, linked to his existing email account since the addresses match). Google's consent screen names the Supabase domain rather than "Runway" until the app passes brand verification or Supabase gets a custom auth domain; left as is for now. After saving the provider in the Supabase dashboard the auth server took about a minute to pick it up.
- **2026-10-22 · A failed Google sign-in now explains itself.** Supabase sends a rejected OAuth sign-up (for example a non-school Google account, refused by the `is_school_email` trigger) back to the site as `?error=…` with no session; the app used to drop that on the landing page, or on whichever account was already signed in on that browser, which looked like "every Google account signs into my account". Boot now moves the message to the sign-in screen (`src/lib/callbackError.ts`) with the school-email wording. The sign-in screen still bounces an already-signed-in person to their runway: sign out first to switch accounts.
- **2026-10-22 · The school-email rule is a switch, off for now.** `app_config.school_email_only` (migration 0011) is read by the sign-up trigger and, through the public `signup_policy()` function, by the sign-in form, which drops its client-side check and changes its wording when the switch is off. Aryen has one school account and wanted to test the new-user path with ordinary accounts, so the live value is `false`. Turn it back on before launch: `update app_config set value = 'true' where key = 'school_email_only'`. Accounts created meanwhile keep whatever domain they signed up with, so classmate matching won't find them a school.
- **2026-10-22 · The app never waits forever for the session check.** A signed-in browser showed only the wordmark: `getSession()` never resolved (a refresh that doesn't return, or supabase-js's cross-tab lock held by a stuck tab), and every screen waits on `ready`. After four seconds the app now opens as signed out and catches up through `onAuthStateChange`. Sign out is now `scope: 'local'`: it ends the session on that device only, so signing out on one browser no longer invalidates another.
- **2026-10-22 · Adding a calendar can't get stuck.** A first sync from the Connect screen hung on "Adding…" (the function request never answered; the scheduled sync processed the same source in a second, and this project has no function log tables to say why). Browser calls to Edge Functions now time out after 45 s with a plain message, and a calendar whose first sync fails stays saved: the 15-minute sync finishes it, and the screen says so with a Continue button instead of inviting a second paste.
- **2026-10-22 · The extension's "Failed to fetch" was CORS**: the functions' shared preflight didn't list `x-runway-token`, so browsers refused the import request before sending it (curl never noticed, it skips preflight). The header is allowed now, and the extension (0.1.1) also asks for host permission on the Supabase project, which bypasses CORS entirely once the unpacked extension is reloaded.
- **2026-10-22 · Signals keep their ranges in the database too.** `signals` (migration 0012) uses `(user_id, day, kind)` as its primary key rather than a separate unique constraint, adds `updated_at`, defaults `source` to `'shortcut'`, and repeats the function's coarse ranges as a check constraint (sleep 0–24 h, exercise 0–1440 min, whole steps 0–200 000, a place needs a label of at most 80 characters), so a row written straight from the app under own-rows RLS can't hold anything finer or stranger than the Shortcut may send.
- **2026-10-22 · Ralph tried and removed.** An autonomous loop ran two iterations on the backlog and produced the `signals` table and the `signals` Edge Function (handler separated from `Deno.serve` so it tests against a fake store; one coarse row per person, day and kind; up to 8 rows per send; same token as the extension; all-or-nothing validation). The work was reviewed, its tests pass (RLS 43, Deno 57) and it is kept. The loop itself, its control files and the tool are gone: two copies started in the same checkout once, and a loop that commits unattended to a repo whose `main` deploys needs more guard rails than it was worth. Work continues by hand from `docs/v2/BACKLOG.md`.
- **2026-10-22 · The iPhone Shortcut gets its own token.** `access_tokens.purpose` now allows `shortcut` (migration 0013) and the `signals` function looks up that purpose, so replacing the extension token doesn't break the Shortcut or the other way round. The guide ("Sleep and exercise from your iPhone") is drawn like the calendar guides, three schematic Shortcuts screens; it sits folded at the bottom of Connect (its body isn't built until opened) and open in Settings, with the address to post to, the token made once, and a "Received from your phone" list so the first manual run can be checked without leaving the page.
- **2026-10-22 · Patterns: numbers in SQL, words in the app.** `signal_patterns(p_user)` (migration 0014, callable only for yourself) groups the last 60 days of sessions and phone signals four ways: after 11 PM vs earlier, nights of 7 h sleep or more vs less, days with 30 min of exercise or more vs less, and place labels with at least three sessions. `src/lib/patterns.ts` turns that into at most four sentences and stays silent below 7 days with sessions, below three sessions on either side, or below a 5-point / half-hour difference. The wording is "tends to" throughout and the section says so.
